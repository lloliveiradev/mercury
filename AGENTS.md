# AGENTS.md

Rules for every coding agent and for people working in this repository. Read this file, then [`docs/README.md`](docs/README.md).

Mercury is a portfolio data platform: public Brazilian datasets are conformed to one municipality-and-time spine, analysed with statistical rigor, and published as reproducible findings. The goal and the decisions behind it are in [`docs/design/brief.md`](docs/design/brief.md) and [`docs/adr/`](docs/adr/).

## How to work

### The owner writes the product code

The project owner writes the product code by hand, on purpose: the project exists to demonstrate and to keep practising engineering skill.

- Do **not** implement product code (pipelines, models, SQL, infrastructure, apps) unless the owner asks for that specific change in the current conversation.
- Agents are welcome for: specs, plans, ADRs, documentation, code review, explaining trade-offs, and tests **when asked**.
- When asked to review, give findings ranked by impact and cite files and lines. Do not rewrite the owner's code in the same step.

### Language

Everything written to this repository is English: code, identifiers, comments, docs, commit messages, issue and pull request text. Conversation with the owner is in Portuguese.

### Documents

- The brief ([`docs/design/brief.md`](docs/design/brief.md)) is the approved target. It changes only with the owner's approval.
- Specs live in [`docs/specs/`](docs/specs/README.md), one per phase: they say **what** must be true when the phase ends, not how to split the work.
- Plans live in `docs/plans/` as `YYYY-MM-DD-phase-NN-slug.md`. A plan includes a pre-mortem: state transitions and re-runs, concurrency, config defaults, side effects before and after commit, and what the phase **removes**.
- ADRs live in [`docs/adr/`](docs/adr/). An accepted ADR is never edited to change its decision: write a new ADR that supersedes it and link both ways. Fixing typos is fine.
- Specs and plans are tool-agnostic. Never create tool-specific doc folders.
- When a document and the code disagree, the code wins and the document is fixed.

### Verify, do not remember

Versions, licences, limits, prices and tool behaviour change. Check the vendor's documentation before stating a fact that a decision depends on. Do not pin or quote a version from memory.

## Data rules

- **No real data, no secrets in git.** Nothing under `data/` is versioned except `data/README.md`. Fixtures are synthetic or generated by code.
- Use only open datasets whose terms allow it. Record each source, its terms and its retrieval date in the dataset manifest.
- Do **not** ingest the personal-level files of any source (for example the "per person" accident files): they carry personal data and the project does not need them (LGPD).
- A credential in a commit is an incident: rotate it, then fix the history. Hooks and CI run gitleaks.

## Statistical honesty rules

These make the analysis defensible. A finding that breaks one is not published.

- Say **association**, never causation, unless the design supports it.
- Control for hour of day, day of week, holidays and each location's seasonal pattern before reporting an effect of weather. Raw correlation of two seasonal series is not a finding.
- Convert every timestamp to one stated time zone before any join; never assume that two sources share one.
- Uncertainty must account for autocorrelation in hourly series.
- Do not estimate effects on real data before the hypotheses are written down.
- When many hypotheses are tested, correct for multiple comparisons and report how many were tried.
- Report effect sizes with intervals, the coverage of each source (federal highways only, stations only where they exist) and the matching distance used to join stations to municipalities.
- Every published number traces to a versioned asset and a passing quality check.
- Every analysis has a recovery test: a synthetic dataset with a known effect must be recovered through the real join, and unrelated series that are autocorrelated and seasonal must not pass as significant after correction.

## Conventions

- Commits follow Conventional Commits; lefthook enforces it. Branches: `phase/<NN>-<slug>` for phase work, `<type>/<short-description>` otherwise. Never commit on `main`.
- Work stays inside the task. Do not refactor, delete or "tidy" files outside it. Suggest, do not do.
- Prefer the smallest change that meets the spec. A new dependency, store or service needs an ADR.

## Verify before you finish

Run what applies to what you changed, and state the result honestly. Today:

```bash
make docs-check      # formatting of Markdown, YAML and JSON
make scan-secrets    # gitleaks over the tree and history
```

Targets for tests, the pipelines and the local stack are added by the phase that creates them. If a check cannot run, say so; do not report it as passing.
